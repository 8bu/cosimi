# simlm — Codebase Map for AI Agents

## What this is

A SimSimi-style pattern-matching chatbot. **No LLM at runtime** — replies come from a curated/learned pattern store, scored by a 3-tier matching engine (exact → Postgres FTS → trigram). Built as a pnpm + Turbo monorepo so the public chat API, the internal admin API, and two Vite/React UIs share typed packages.

## Tech stack

- **Runtime:** Node.js 22, pnpm 11 (pinned via `packageManager`), Turbo 2.
- **Backend:** Hono.js on Node, Postgres 16 (FTS + `pg_trgm`).
- **Frontend:** Vite + React, Tailwind v4.
- **Tooling:** TypeScript 5.7, oxlint + oxfmt (oxc-project), tsx, valibot for env parsing, pino for logging, vitest for tests.

## Monorepo layout

```
apps/
  api/         # public Hono REST + SSE, binds PORT on 0.0.0.0
  admin-api/   # internal Hono REST, binds ADMIN_PORT on 127.0.0.1
  web/         # public chat UI (Vite + React + Tailwind v4, scaffolded Phase 9)
  admin/       # internal admin dashboard — stub only, lands Phase 12+
packages/
  config/      # valibot env schema
  types/       # shared DTOs
  normalizer/  # pure NFC + case + whitespace normalizer
  db/          # postgres client, migrations, repositories
  matcher/     # 3-tier matching engine
  logger/      # pino + redactInput() — shared by api + admin-api
  ui-tokens/   # pure-CSS design tokens (Tailwind v4 @theme block) — shared by apps/web (and later apps/admin)
  tsconfig/    # shared tsconfig bases
  oxlint-config/ # shared oxlint ruleset (JSON)
seeds/
  vi/          # hand-curated Vietnamese seeds
  chatterbot/  # snapshot of chatterbot-corpus YAML
docs/          # phased specs — see below
```

## Where the specs live

Phased build plan in `docs/SPEC_PHASE_0.md` … `docs/SPEC_PHASE_15.md`. Each spec includes Goals, Layout, Deliverables, Acceptance, and Prev/Next pointers. `docs/REQUIREMENTS.md` holds the top-level product brief. **Always read only the current phase's spec unless the work demands cross-phase context** — resist reading ahead.

## Key commands

- `pnpm dev:all` — one-shot start: Docker-daemon guard → `db:up --wait` → `migrate` → `dev`. Use this as the default. Falls back to a clear stderr message + exit 1 if the Docker daemon isn't reachable.
- `pnpm dev` — turbo dev across all apps (api + admin-api + web). Assumes Postgres is already up and migrated; use `dev:all` to chain those.
- `pnpm db:up` / `pnpm db:down` / `pnpm db:reset` — Postgres dev container. `db:up` uses `docker compose --wait`, blocking until the `pg_isready` healthcheck passes — chaining `migrate` immediately after is safe.
- `pnpm migrate` / `pnpm seed` / `pnpm seed:chatterbot` — db management via `@simlm/db`. The root `migrate` script forwards the `up` subcommand by default; for `status` or `reset`, run `pnpm --filter @simlm/db migrate <subcommand>`.
- `pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build` — turbo fan-out.

## Conventions

- **Workspace package naming:** every internal package is `@simlm/<name>` and `private: true`. Cross-package imports go through `@simlm/...` specifiers; pnpm wires them via `link-workspace-packages=true`.
- **Supply-chain embargo:** `pnpm-workspace.yaml` sets `minimumReleaseAge: 10080` (7 days). New deps published less than a week ago will refuse to resolve; the lockfile is the only thing that touches this gate, so CI's `--frozen-lockfile` is unaffected. To force-include an emergency patch, add it under `minimumReleaseAgeExclude` and review like normal code.
- **Postinstall allowlist:** `allowBuilds` in `pnpm-workspace.yaml` is the per-package permission list for postinstall scripts. Every entry is permission to run arbitrary code at install time — add deliberately, document why.
- **admin-api is a separate process bound to `127.0.0.1`:** the public `api` and internal `admin-api` never share a process. The admin API only accepts loopback connections; exposing it externally requires deliberate reverse-proxy work. This split is the security boundary, not a stylistic choice.
- **No LLM at runtime:** never add OpenAI/Anthropic/etc. SDKs to `apps/api`. The matcher in `@simlm/matcher` is the only thing that produces replies.
- **Env loading is a function call, not a module-load side effect.** `@simlm/config` exports `loadEnv()` — each consumer (api, admin-api, logger) calls it *once at startup*, not at import time. Importing the module does not read `process.env`, which keeps the module graph pure and lets tests inject synthetic env via `v.parse(EnvSchema, fakeEnv)`. Do not introduce a top-level `export const env = loadEnv()` singleton — that re-couples imports to the environment.
- **Diacritic-stripping split:** `@simlm/normalizer` does NFC + lowercase + whitespace **but preserves diacritics**. Postgres handles diacritic-stripping server-side via the `f_unaccent(text)` `IMMUTABLE` wrapper around the `unaccent` extension (defined in `001_extensions.sql`). All three matching tiers compare against `f_unaccent(...)`, never raw `unaccent(...)` — the underlying `unaccent()` is `STABLE`, which Postgres refuses to embed in expression indexes or generated columns. Both write-time and query-time paths run the same JS→SQL pipeline, so the comparison key stays symmetric. Do not add `.replace(/[̀-ͯ]/g, '')` or similar to the JS normalizer — it would diverge from the server side.
- **`pairs.normalized_unaccented` is `GENERATED ALWAYS AS (f_unaccent(normalized_input)) STORED`.** Writers update `normalized_input`; Postgres regenerates the unaccented form. Never `INSERT` or `UPDATE` `normalized_unaccented` directly — Postgres rejects it with `cannot insert a non-DEFAULT value into column`. The column is `STORED` (not virtual) precisely so all three matching indexes can sit on it.
- **Migration discipline:** files in `packages/db/migrations/` are numbered, additive, and **never rewritten after merge** — once a migration is on `main`, new schema changes go in a new file. The `_migrations` tracking table records what's been applied; the runner refuses to re-apply or re-order existing files. `pnpm migrate reset` is dev-only — guarded by a `NODE_ENV !== 'production'` check in `migrate.ts` and meant for blowing away the local dev DB to start clean.
- **One canonical write path for `pairs`.** `@simlm/db` exports `insertPair` and `insertManyPairs` — every writer (the seed CLI, the eventual admin import endpoint, admin-manual-add) goes through these. The bulk helper deliberately enumerates columns: `input`, `normalized_input`, `response`, `source`, `topic`, `batch_id`, `flagged`. **Never list `normalized_unaccented`** in that column list — Phase 2 made it `GENERATED ALWAYS … STORED` and Postgres rejects explicit values for it. Normalization happens once in JS via `@simlm/normalizer`; the unaccented form is regenerated server-side.
- **`@simlm/db` subpath import aliases.** The package exposes only `.` to outside consumers (the public surface). Internally it uses `#client`, `#repositories/*`, and `#scripts/*` — defined in `packages/db/package.json`'s `imports` field. New repository or script files automatically resolve under the wildcard, so adding `packages/db/src/repositories/foo.ts` is importable as `#repositories/foo` without touching `package.json`. Outside the `db` package, always import via `@simlm/db`, never via `#`.
- **Seed CLI format detection.** `packages/db/src/scripts/seed.ts` dispatches by file extension: `.json` (array), `.jsonl` (one object per line), and `.yaml`/`.yml` (flat list, unless the file has a top-level `conversations:` or `categories:` key — then it's parsed as chatterbot-corpus and flattened with a sliding window over each thread). Format is positional; no per-file flag. Globs are expanded by the shell, not the CLI.
- **Every seed run creates an `import_batches` row.** `seedFile()` calls `createBatch` → `insertManyPairs(..., batch_id)` → `setBatchCount`. The batch row is the unit of rollback (used by the admin endpoint in Phase 6), so the seed CLI must never bulk-insert without one. Re-running a seed is **expected** to create duplicate rows — the per-batch `note` records the source file path and the batch id, so duplicates are traceable and roll-back-able.
- **Root convenience scripts invoke `tsx` directly, not `pnpm --filter`.** `pnpm seed:vi` etc. run `tsx packages/db/src/scripts/seed.ts seeds/vi/*.yaml` from the workspace root, because `pnpm --filter <pkg> exec` would `cd` into `packages/db/` and the shell's glob expansion would then fail to match `seeds/vi/*` (which lives at the repo root). The `#client` / `#repositories/*` subpath imports still resolve correctly because Node looks up subpath imports against the nearest `package.json` containing the importing file, which is `packages/db/package.json` regardless of cwd.
- **`seeds/chatterbot/` is a frozen upstream snapshot.** Files are copied verbatim from `gunthercox/chatterbot-corpus` at the commit SHA pinned in `seeds/chatterbot/NOTICE`. The directory is in `.oxfmtignore` so re-formatting can't drift the snapshot away from the upstream pin. BSD-3 attribution lives in the root README; the full license text is `seeds/chatterbot/LICENSE`. **No postinstall network fetch** — refreshing is a manual, deliberate act (bump the SHA in `NOTICE`, re-fetch the four `.yml` files at that SHA, re-seed).
- **Matcher cascade is `session_teach → exact → FTS → trigram`, short-circuit on first non-null.** `@simlm/matcher` exports `match({ normalizedInput, sessionId })` plus the four tier functions individually (`sessionTeachTier`, `exactTier`, `ftsTier`, `trigramTier`). Caller is responsible for normalizing input *before* calling — the matcher never invokes `@simlm/normalizer` itself, so the same `match()` is reusable by an admin tool that wants to probe arbitrary raw strings. The session-teach tier is skipped entirely when `sessionId` is `null`. `lowConfidence` is set iff `tier === 'trigram'`; FTS `ts_rank` is clamped to `[0, 1]` for UI uniformity. Top-K random pick (env `MATCH_TOP_K`, default 5) happens *in JS*, after Postgres has ordered by tier-score → `score DESC` → `id DESC`. Do not push the random pick into SQL — losing the SQL ordering would make `score DESC` tiebreaking unobservable in tests.
- **All three pair-matching tiers compare `pairs.normalized_unaccented` (server-generated) against `f_unaccent(${normalizedInput})` (query-time).** This is the symmetric write/read pipeline. The session-teach tier is the odd one out: `session_teaches.normalized_input` has *no* generated unaccented column (10-min TTL keeps the table tiny), so both sides run `f_unaccent` at query time. If session_teaches ever grows, add a functional index `(session_id, f_unaccent(normalized_input))` rather than a stored generated column — keeps the schema minimal.
- **Trigram tier double-filters: `%` index op AND explicit `similarity(...) >= MATCH_TRGM_MIN`.** The `%` operator's threshold is the Postgres GUC `pg_trgm.similarity_threshold` (default 0.3, process-global, mutable via `set_limit()`). We don't trust the GUC — the explicit similarity filter pins the threshold to our env, which makes matcher behavior deterministic regardless of server-side configuration drift. Never replace the explicit filter with `set_limit()`.
- **The matcher test DB is a separate Postgres database (`simlm_test`), not a schema namespace inside `simlm`.** Vitest's `globalSetup` (`packages/matcher/test/global-setup.ts`) connects to the `postgres` maintenance DB to `CREATE DATABASE simlm_test` if missing, then drops/recreates `public` and applies every migration from `packages/db/migrations/` in order. The migration loop is inlined here (5 lines) rather than imported from `@simlm/db` because `migrate.ts` is a CLI script — refactoring it to expose `applyMigrations()` is fine if a second package ever needs the same setup. `process.env.DATABASE_URL` is rewritten to `…/simlm_test` *both* in `globalSetup` and in the `setupFiles` (`test/setup-env.ts`); the second write is defensive belt-and-suspenders against worker-thread env propagation edge cases.
- **`MATCH_FTS_MIN` is lowered to `0.01` in matcher tests, not the production default `0.1`.** `ts_rank` with the `simple` text-search config produces values <0.1 for short 2-token queries against 5-token docs, which is why production filters them out. Tests want the FTS tier to *fire* on fixture queries, so the threshold is dropped in `packages/matcher/test/setup-env.ts`. If you add an FTS-tier test that asserts a *high*-confidence match, raise the threshold locally in that test rather than changing the shared default.
- **Matcher test fixtures go through `@simlm/db`'s `insertManyPairs` — never raw `INSERT INTO pairs`.** Same canonical-write-path rule as production. Soft-deletion in tests is an `UPDATE pairs SET deleted_at = NOW()` *after* the insert, so we get the row's id first. `session_teaches` inserts in tests *do* use raw SQL because there's no repository helper yet (Phase 5 will add `/teach`). When that helper lands, switch tests over.
- **Matcher test pool is `threads` with `singleThread: true` and `fileParallelism: false`.** All test files share one Postgres database; parallel execution would stomp on fixtures. If you add more matcher test files, either keep this serial pool or scope each file's fixtures to a unique key (e.g., a per-file session_id namespace).
- **`withSession` middleware consumes the request body once and stashes it on context.** `apps/api/src/lib/session.ts` calls `c.req.json()` exactly once (Hono's body stream is single-use) and stuffs the result under `c.set('parsedBody', body)`. Route handlers must read `c.get('parsedBody')` — never call `c.req.json()` again, or you'll get "body already used." The middleware also resolves `session_id` from (body → `X-Session-Id` header → minted) and always echoes the chosen id in the `X-Session-Id` response header. A `declare module "hono"` block in the same file types `c.get('sessionId')` and `c.get('parsedBody')` so downstream code doesn't need casts.
- **SSE error visibility: TeachError messages are user-facing, every other error is generic.** The `/chat` handler's catch arm in `services/chat-handler.ts` discriminates: `err instanceof TeachError` → emit `err.message` (e.g. "reply too long", "I don't know what to teach about…"); anything else → emit `"teach failed"` and log the full diagnostic via pino. `services/rate-limit.ts` deliberately throws a plain `Error` to avoid a circular import with `teach-handler`; the teach handler catches it and rewraps as `TeachError` so the rate-limit message still reaches the client. The SSE outer wrapper (`lib/sse.ts`) catches anything that escapes the generate callback and emits `"internal error"`, never a stack trace.
- **Every SSE response ends with the literal frame `data: [DONE]\n\n`.** This is the OpenAI/Anthropic convention and is written from a `finally` block in `streamChat`, so it fires even when the generator throws. The `ChatStreamEvent.type === 'done'` variant in `@simlm/types` is reserved for clients that want a structured terminator; the wire-level terminator is always the `[DONE]` literal.
- **Interval arithmetic in templated SQL uses `n * INTERVAL '1 unit'`, not `(n || ' unit')::interval`.** postgres.js types JS numbers as `int4`/`int8`, and `int || text` raises `operator does not exist`. The session and session_teach upserts (`services/chat-handler.ts`, `services/teach-handler.ts`) both use `NOW() + (${n} * INTERVAL '1 hour'/'1 minute')`. If you need an interval whose unit is also dynamic, build the value in JS and pass it as text.
- **`BIGSERIAL` ids round-trip as strings through postgres.js by default.** `teach_queue.id` is returned to the client in the `teach_ack` SSE event as a `number`, which means the handler must explicitly cast: `RETURNING id::int AS id` (see `services/teach-handler.ts`). Same trap shows up in tests — `apps/api/test/helpers.ts`'s `seedPairs` selects `id::int AS id` so the returned values can be POSTed straight into JSON bodies that validate against `v.number()`. The matcher's tier functions still return ids as strings (they only compare them — never serialize), and that's a Phase 4 concern; don't refactor it from Phase 5.
- **SSE responses must be drained in tests that issue dependent follow-up requests.** `app.fetch()` returns a `Response` whose body is a buffered stream; the chat handler runs concurrently inside it. If a test posts a `/teach` then a `/chat` to the same session without consuming the first body, the second request can observe a half-applied transaction — or worse, race with the next test's `TRUNCATE` and produce a Postgres deadlock on `sessions`. `apps/api/test/helpers.ts` exports `drain(res)` (just `res.text()`) for this; `consumeChatStream(res)` drains as a side effect of parsing events. Even header-only assertions (`expect(res.headers.get('x-session-id'))…`) must call `drain` before the test exits.
- **`apps/api/test/global-setup.ts` reuses the same `simlm_test` database as `@simlm/matcher`.** The migration loop is inlined (mirrors `packages/matcher/test/global-setup.ts`) because `@simlm/db` doesn't export an `applyMigrations()` — `migrate.ts` is a CLI. Tests in this package use the same `pool: 'threads'`, `singleThread: true`, `fileParallelism: false` settings as matcher tests, for the same reason: one database, no parallel stomp. The shared setup also pins `SSE_DELAY_BASE_MS=0` and `SSE_DELAY_JITTER_MS=0` so token pacing doesn't blow per-file timeouts. **`apps/admin-api/test/global-setup.ts` is the third copy of this migration loop** — that's the threshold at which a shared `applyMigrations()` helper is worth extracting. Don't add a fourth inlined copy; refactor instead.
- **`apps/admin-api` binds `127.0.0.1:ADMIN_PORT` by default; non-loopback bind is a soft warn, not a refusal.** Security is a *deployment property* — "is this socket reachable from outside the host?" — not a per-route audit. `apps/admin-api/src/index.ts` checks `env.ADMIN_HOST` against `127.0.0.1` / `localhost` / `::1`; anything else logs a `warn`-level breadcrumb ("ensure a network-layer gate is in place") and continues. The user opted out of build-in auth; the warn is the only audit trail. **Don't add application-layer auth to admin routes** — the entire process is the admin surface (no `/admin/*` prefix), and adding auth would imply the routes might be safe to expose externally, which is false. The split-process model means a misconfigured `apps/api` network exposure cannot leak admin functionality; that property is worth more than per-route guards.
- **Admin teach-queue approval uses the canonical `insertPair` write path inside a transaction.** `apps/admin-api/src/routes/teach-queue.ts` calls `insertPair({...}, tx)` rather than a raw `INSERT INTO pairs`, both to honor the canonical-write-path rule (the generated `normalized_unaccented` column rejects explicit values) and to keep the queue UPDATE + pair INSERT atomic. To make this composition work, `@simlm/db`'s `insertPair` and `insertManyPairs` now accept an optional `Executor` (postgres.js `Sql | TransactionSql`) as their second arg. Outside transactions, omit it — the default `sql()` pool client is used. **Never call `insertPair()` without `tx` from inside a `.begin(async (tx) => {...})` block** — you'd lose the transaction's atomicity guarantee silently.
- **`insertPair` and `createBatch` use `RETURNING id::int AS id` to keep wire shapes numeric.** BIGSERIAL ships as a string by default through postgres.js; the cast lands `number` ids in the helpers' return types. This matters because the admin `/import` endpoint returns `batch_id` to clients verbatim, and `/rollback` then accepts a body whose valibot schema requires `v.number()` — without the cast, the round-trip would 400. Same applies to teach-queue approve returning `pair_id` and `/pairs` POST returning `id`. The pattern is "cast at the canonical write boundary", not "cast at every read site."
- **`/rollback` re-runs are no-ops by design.** The `UPDATE pairs SET deleted_at = NOW() WHERE deleted_at IS NULL AND <filters>` guard means a second rollback with the same body returns `affected: 0` — already-deleted rows are untouched. This is the "batch is the unit of rollback" discipline (see seed CLI section above) cashing in: each `import_batches.id` is rollback-safe regardless of how many times it's invoked. Don't add a separate "purge" or "hard-delete" path; soft-delete is the contract, and the partial indexes on `deleted_at IS NULL` keep the cost zero for active reads.
- **`/import`'s JSONL streaming bypasses Hono's buffered body parser.** Reading `c.req.raw.body!.getReader()` directly is what makes 10k-row imports OOM-safe — `c.req.json()` or `c.req.text()` would buffer the entire request before parsing. The `FLUSH_AT=500` constant in `apps/admin-api/src/routes/import.ts` bounds the in-memory batch; every flush goes through `insertManyPairs` (which uses postgres.js's multi-row VALUES helper for one round-trip per batch). Each `/import` call creates exactly one `import_batches` row whose id becomes every inserted pair's `batch_id`, so the rollback surface stays per-call, not per-row.
- **Admin `/pairs` PATCH builds SET clauses as conditional sql fragments, not via `sql(obj, ...cols)`.** postgres.js's object-helper treats every record value as a parameter literal — so a `Fragment` like `sql\`NOW()\`` becomes the text representation of the fragment, not interpolated SQL. The chain-of-fragments approach in `pairs.ts` (`db\`, input = ${b.input}\`` etc.) lets `updated_at = NOW()` stay a literal expression while user-supplied fields stay parameterized. Same pattern in `/rollback` — empty `db\`\`` fragments compose cleanly into a templated WHERE.
- **LLM bulk-import operator doc lives at `docs/LLM_IMPORT_FORMAT.md`.** URLs in it reflect Phase 6's actual `http://127.0.0.1:3001/<route>` shape (no `/admin/*` prefix), not the `/admin/*` prefix the early Phase 7 draft assumed. If you reshape admin-api routes (add a prefix, change the default port, etc.), update the doc's curl recipes in lockstep — it's operator-facing and the spec recipes are the documented contract. The 200-char prompt-side cap on `input`/`response` is *advisory* (LLM-instruction-level); the server's actual valibot cap is 2000.
- **GC lives in-process in `apps/api`, not a separate worker.** `apps/api/src/lib/gc.ts` spins a single `setInterval` (period = `GC_INTERVAL_MS`, default 5min) that DELETEs expired rows from `sessions` and `session_teaches` in parallel. The interval handle is **`.unref()`'d** at registration — without that, Node's event loop would refuse to exit even after `server.close()` resolves on shutdown. `SIGINT`/`SIGTERM` calls `stopGc()` first, then `server.close(() => process.exit(0))`; that's the orderly path. Zero-row sweeps stay silent (`log.info` only fires when `sessions + teaches > 0`) — log noise discipline. If we ever go multi-instance, this becomes a Postgres advisory-lock dance or a dedicated worker, not a per-instance race; out of scope for MVP.
- **PII redaction is belt-and-suspenders: pino path-redact AND `redactInput()`.** `@simlm/logger`'s `createLogger` ships a `redact.paths` list (`input`, `response`, `reply`, `message`, `body.message`, `body.reply`, `body.input`) so an accidental `log.info({ input: rawText })` at any level becomes `[REDACTED]`. The explicit `redactInput(text)` helper converts text to `{ length, hash: sha256[..8] }` for cases where you *do* want to log a non-reversible reference (size + identity). Convention: at INFO+ use `redactInput()` if you need to log anything about the text; at DEBUG, raw values go under `*_dbg`-suffixed field names so the redact list won't strip them. Both `apps/api/src/lib/logger.ts` and `apps/admin-api/src/lib/logger.ts` are thin `createLogger('<app>')` re-exports — **never** construct a pino instance directly in an app or you break the PII contract by skipping the shared redact config.
- **`/healthz` runs a 1s-budgeted DB ping; the timeout's setTimeout is `.unref()`'d.** Both api and admin-api's health route race `sql\`SELECT 1\`` against a 1s `setTimeout`. The timer is unref'd *and* cleared in a `finally` — unref is the safety net so an in-flight slow ping during SIGINT/SIGTERM shutdown doesn't keep the event loop alive past `server.close()`. Response shape on 200: `{ ok: true, db: 'up', db_latency_ms: <ms>, uptime_s }`; on 503: same shape with `db_latency_ms: null`. The two route files are identical copies — if you touch one, touch the other (and if a third health check ever needs the same shape, extract to a shared helper).
- **Tokens are shared via `@simlm/ui-tokens`; shadcn primitives are not.** `packages/ui-tokens/theme.css` holds a Tailwind v4 `@theme { ... }` block of CSS variables (warm-neutral surfaces, terracotta primary, serif chat body). Both apps/web and (later) apps/admin `@import` it from their `globals.css`. Per the shadcn-ui design philosophy, the component primitives themselves (`button`, `dialog`, `dropdown-menu`, etc.) are **copied per-app** under `apps/<name>/src/components/ui/*` — never extracted to a workspace package. Reason: token edits should propagate (visual identity stays coherent); component customizations should stay local (per-app freedom to deviate). If you find yourself "DRYing up" a primitive into a shared package, stop — you'll be fighting shadcn's customization model.
- **Tailwind v4 uses CSS-first config — no `tailwind.config.{ts,js}`.** Configuration lives entirely in `apps/web/src/styles/globals.css` via `@import "tailwindcss"` then `@import "@simlm/ui-tokens/theme.css"`. The `@theme` block inside the imported file is what Tailwind v4 reads for design tokens; there is no PostCSS chain and no JS config. The Vite plugin is `@tailwindcss/vite`. If a contributor adds a `tailwind.config.ts`, it's a regression — the v4 CSS-first model is deliberate so that the shared token package can be a single CSS file rather than a JS preset.
- **`apps/web` Vite dev proxy: `/api/*` → `http://localhost:3000` with `/api` stripped.** The api process binds public routes at the *root* (`/chat`, `/feedback`, `/stats`, `/healthz`) — there is no `/api` prefix server-side. The SPA uses `/api/*` as a stable client-side namespace so:
  1. Production reverse proxies can route `/api/*` to the api process without touching non-api routes (static assets, future `/auth` etc.).
  2. The api process never has to learn about the `/api` prefix (mirrors the convention used by admin-api too — no `/admin/*` prefix there either).
  The rewrite lives in `apps/web/vite.config.ts`; the same rewrite must exist in whatever reverse proxy fronts production.
- **`allowBuilds` in `pnpm-workspace.yaml` is the postinstall permission list.** Each entry is permission to run arbitrary code at install time. Add deliberately, only when `pnpm install` reports a build was blocked, and document *why* the postinstall is needed. Current entries:
  - `esbuild: true` — `tsx` ships esbuild; postinstall fetches the platform-specific native binary.
  - `@swc/core: true` — `@vitejs/plugin-react-swc` (apps/web) uses `@swc/core`; postinstall fetches the platform-specific native binary; without it Vite's React transform can't load.
  - Never add wildcards; never silently bump entries.
- **Workspace-shared tests against `simlm_test` race when run in parallel.** `packages/matcher`, `apps/api`, and `apps/admin-api` each have a `vitest globalSetup` that drops + recreates `public` in the shared `simlm_test` database. `pnpm -r test` runs packages concurrently by default and will stomp those setups on top of each other (you'll see migration 001 fail with `42883` because the extension was just dropped by the racing setup). Run with `pnpm -r --workspace-concurrency=1 test` or filter to one package at a time. Adding a fourth such suite is the threshold at which a shared `applyMigrations()` helper plus a single coordinated setup is worth extracting — don't paper over the race with retries. (`apps/web`'s vitest suite is DB-free — it tests `parseSseStream` over an in-memory `ReadableStream` — so it can run in parallel; the rule above only applies to the DB-touching suites.)
- **Public-API DTOs live in `@simlm/types` and are imported by both sides.** `apps/api` route handlers declare their JSON return as `const payload: <Type> = …; return c.json(payload)`; `apps/web`'s `apiJson<T>(…)` callers re-import the same `T`. Don't re-declare response shapes in `apps/web/src/api/*` — if a server route adds a field, only `packages/types/src/index.ts` should change. The Phase 10 additions (`FeedbackResponse`, `HealthResponse`) reflect routes whose shapes were inlined client-side in the original spec; that drift is what this rule prevents.
- **SSE consumer is hand-rolled, lives in `apps/web/src/lib/sse-parser.ts`, and treats `[DONE]` as a stream-end sentinel (not a JSON payload).** It is an async generator over `ReadableStream<Uint8Array>` because `EventSource` is GET-only and we POST a body. Frames split on `\n\n`; bytes past the last `\n\n` stay buffered for the next chunk (chunk-split-mid-frame is normal). The structured `{ type: 'done' }` event in `@simlm/types` is for `switch` exhaustiveness — the wire-level terminator is always the literal `data: [DONE]\n\n` frame, written from a `finally` block on the server even on errors. The parser's `finally` calls `reader.releaseLock()` so an aborted stream (caller passed an `AbortSignal` to `fetch`) doesn't leave the response body in a locked state. Don't pull in a library here — the protocol is ~30 LOC and our wire shape is a custom discriminated union anyway. Tests at `apps/web/src/lib/sse-parser.test.ts` cover happy path, chunk-split-mid-frame, trailing-buffer, `[DONE]`-only stream, malformed-JSON tolerance, and abort/lock-release; they need no globalSetup.
- **Session id is server-canonical; the client adopts whatever `X-Session-Id` comes back.** `withSession` middleware echoes the id on *every* response, including the very first request where the client sent none. `apps/web/src/api/client.ts`'s `apiFetch` reads the header and writes through `sessionStore.getState().setSessionId(echoed)` if it differs from the in-memory value. The store (`apps/web/src/store/session.ts`) uses zustand's `persist` middleware under the localStorage key `simlm.session`, so the id survives reloads. Never `crypto.randomUUID()` on the client — duplicating UUID generation invites split-brain when the server reissues (malformed/expired ids).
- **`apiFetch`'s `raw: true` is load-bearing for streaming endpoints.** Two reasons: (1) the response body must stay un-consumed for `parseSseStream` to read it; (2) on a 4xx/5xx the streaming caller decides what to do — without `raw: true`, `apiFetch` would call `res.json()` to build an `ApiError`, consume the body, and the downstream stream parser would throw an opaque "body already used" error. Use `raw: true` exclusively for `streamChat` and any future streaming wrapper; the JSON endpoints (`useFeedback`, `useStats`, `fetchHealth`) go through `apiJson` and benefit from the default error mapping.
- **`API_BASE` is `import.meta.env.VITE_API_BASE ?? '/api'`.** Default `'/api'` pairs with the Phase 9 Vite proxy strip (`/api/foo` → `:3000/foo`) — production deployments behind a co-located reverse proxy should keep this default and configure the proxy to do the same rewrite. Override `VITE_API_BASE` only when the SPA is served from a different origin than `apps/api`; that's the only case where CORS becomes an additional concern (one-line `hono/cors` addition on the api side).
